    Primero el contrato, después el código

    Estos tres archivos son la única fuente de verdad del sistema. A partir de ellos npm run proto:gen genera los tipos de TypeScript de cada microservicio: si alguien cambia un campo, el proyecto deja de compilar hasta que todos se actualicen. Lo que ves aquí se lee del disco del servidor en tiempo real. 

      Cargando contratos…

      Cómo se comunican los microservicios

      Los navegadores no pueden hablar gRPC nativo porque no controlan los frames de HTTP/2. Por eso el gateway traduce: hacia adentro todo es gRPC con Protobuf binario; hacia el navegador, WebSocket. No existe ningún endpoint REST ni verbos GET/POST de negocio.

      REST + JSON frente a gRPC + Protobuf

      REST + JSONgRPC + Protobuf
      Qué exponeRecursos (URL + verbo)Funciones remotas tipadas
      FormatoTexto, se parsea en cada peticiónBinario compacto (~70 % menos aquí)
      TransporteHTTP/1.1, una petición por conexión a la vezHTTP/2 multiplexado: las 4–6 ambulancias comparten una sola conexión TCP
      StreamingNecesita WebSocket o SSE aparteNativo: servidor, cliente y bidireccional
      ContratoOpcional (OpenAPI)Obligatorio (.proto) y genera código
      En contra—No se puede leer a simple vista, el navegador necesita un gateway y depurar exige herramientas

      Tipado de punta a punta

      1. Contratoproto/*.proto define mensajes y servicios.
      2. Generaciónproto-loader-gen-types crea las interfaces en src/generated.
      3. CompilaciónSi un handler devuelve un campo que no existe, tsc falla.
      4. EjecuciónLos tipos desaparecen al compilar, así que Zod parsea cada paquete. Prueba “Falla de sensor”.

      Por qué la simulación ya no es infinita

      El turno se inicia cuando entra el primer visitante y se apaga solo 45 segundos después de que se va el último, o al cumplir 10 minutos. Sin nadie mirando, los tres microservicios quedan en reposo y el contenedor gratuito casi no consume CPU.
